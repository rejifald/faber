# ADR-0015: Releases are signed on the builder, not attested in CI

## Status

**Superseded 2026-10-09 by
[ADR-0031](0031-releases-are-signed-by-github-from-a-fresh-public-repository.md)
for the signing key.** From the auth cut on, GitHub's keyless attestation signs
every release, and no key is held anywhere. The rules this ADR set around the key
still stand: verification fails closed, it runs before any binary is fetched, and
it checks against a trust root compiled into the follower.

accepted (2026-09-03). Supersedes the verification mechanism ADR-0006 acquired
in [#41](https://github.com/rejifald/faber-legacy/issues/41); everything else about the
update channel is unchanged. Unblocks [#50](https://github.com/rejifald/faber-legacy/issues/50).

## Context

[#41](https://github.com/rejifald/faber-legacy/issues/41) gave the channel authenticity
via Sigstore keyless attestation: `release.yml` minted provenance from its own
OIDC identity, and a follower ran `gh attestation verify` over `SHA256SUMS`
before downloading anything. Fail-closed, no opt-out.

Cutting the first release under it failed:

```
Failed to persist attestation: Feature not available for user-owned private
repositories. To enable this feature, please make this repository public.
```

That is not a configuration mistake. GitHub's attestation API is unavailable for
private repositories unless they are **enterprise**-owned — a free, Pro or Team
organization fails identically ([github/docs#35835](https://github.com/github/docs/issues/35835):
*"If the repository is private, it must be owned by an enterprise."*). So the
choices were: go public (gated on an unrelated, still-open decision), buy
Enterprise Cloud, sign releases ourselves, or abandon fail-closed verification.

Re-reading #41's own threat model while deciding made the answer easy, because
keyless was already the weaker mechanism for faber's actual risk:

> This authenticates the channel, not the code. A compromised repo that can also
> run the release workflow produces a validly-attested malicious release.

That is not a footnote. For a single-operator project, "someone got write access
to the repo" *is* the realistic compromise, and it is exactly the one keyless
does not stop.

## Decision

**The operator signs `SHA256SUMS` with a key CI cannot reach, and the follower
verifies it against a key list compiled into its own binary.**

### The key never touches GitHub

An `ed25519` key on the builder Mac, held in the login keychain
(`ssh-add --apple-use-keychain`), generated by `deploy/signing-setup.sh`.

The obvious alternative — a GitHub Actions secret, so `release.yml` keeps doing
the work — **defeats the entire purpose** and is worth naming so nobody
reintroduces it as a convenience. Anyone who can add a workflow can exfiltrate a
repo secret, so a key stored there is a key an attacker with repo access holds.
That is strictly worse than keyless, which at least has no key to steal.

### The trust root ships inside the follower

`ACCEPTED_SIGNERS` in `src/update.rs` is a compiled-in constant, and the
`allowed_signers` file is generated from it at verify time rather than read from
disk.

This is the property everything else rests on. An attacker with full repo access
can change that constant in `main`, but that only affects hosts installing a
build carrying the change — and to ship such a build they would have to sign a
release, which they cannot. **An already-installed follower keeps trusting the
keys it was compiled with, whatever the repo says.** A trust root on disk, or one
fetched from the repo, would not have that property.

The corollary is a real constraint, not a detail: rotating a key requires one
release signed by an *existing* key that carries the new one.

### Two keys, from the start

Primary on the Mac; a cold backup generated at setup, moved off the machine, and
signing nothing until it must.

Without it, one dead Mac means every installed host trusts a key nobody holds:
no release is installable ever again and every host needs a manual reinstall. The
list has to contain the backup from day one, because adding a key later needs a
release signed by a key you no longer have.

### CI drafts; the builder signs and publishes

`release.yml` builds every platform, checksums, and creates the release **as a
draft** — then stops. `deploy/release.sh` downloads `SHA256SUMS`, signs it,
**verifies its own signature against the same key list the fleet uses**, uploads
`SHA256SUMS.sig`, and only then flips the draft to published.

The ordering preserves what attest-before-publish gave us: a follower tracks
`/releases/latest`, which excludes drafts, so a release is never visible in a
state where it cannot be verified. Publishing first would open a window in which
the whole fleet sees an unsigned release, refuses it, and records a fault against
a version that was fine.

The self-verify step exists because a signature the fleet cannot check is worse
than no signature — it publishes something every host then refuses.

### What the signature actually claims

CI computes the checksums, and the builder cannot rebuild the Linux binaries to
check them. So the signature means **"the operator deliberately released this
build"** — not "the operator verified these bytes".

That is worth stating plainly rather than letting the ADR imply more. It closes
the threats that matter here (nobody publishes an installable release without the
operator's key, and a repo takeover does not yield one) and it does not make CI
trusted. Closing *that* would need reproducible builds and independent
verification, which is a different project.

### Sigstore attestation stays, demoted

The `Attest the assets` step remains in `release.yml`, conditional on the repo
being public and `continue-on-error`. It costs nothing, it returns on its own the
day the repo flips, and it gives third parties something to check that does not
depend on trusting our key distribution. It is not the gate and cannot block a
release.

## Consequences

- **Releases work while the repo is private**, on any plan, with no purchase.
- **The repo-takeover threat #41 left open is now closed**, which was the point
  of taking this seriously rather than treating it as a workaround.
- Verification uses `ssh-keygen -Y verify`, present with OpenSSH on macOS and
  every mainstream Linux, so no new dependency and no new crate. A stripped
  container without `openssh-client` cannot verify — it refuses, loudly.
- `SIG_NAMESPACE` domain-separates release signatures, so a signature the
  operator made with the same key for anything else (a git commit, an email)
  cannot be replayed as a release signature.
- **The first signed release needs a manual install on every host.** A host
  running a binary that predates `ACCEPTED_SIGNERS` has no way to verify anything
  and refuses everything. This is a one-time cost, and it is the correct
  direction to fail.

  > **Corrected 2026-09-23.** True only of a host on an *unreleased* build that
  > carries #44's attestation check or an empty key list — in practice the
  > builder, which installs from source anyway. The fleet then ran an earlier
  > release whose updater checks SHA-256 digests only and installs whatever is
  > published next, signed or not. So the first signed release installs itself,
  > and its key list is load-bearing: it becomes every follower's trust root for
  > all later releases. Published with `ACCEPTED_SIGNERS` empty, it would strand
  > the whole fleet. `deploy/release.sh` refuses that in preflight.
- A build with an empty `ACCEPTED_SIGNERS` refuses every release. That is the
  state the tree ships in until `signing-setup.sh` has been run, so it is the
  state a mistake most likely leaves it in; a test pins the behaviour.
- The builder is now load-bearing for *publishing*, not just for deciding. A
  release cannot be completed from CI alone. Given ADR-0006 already made the
  decision a deliberate human act, this is a smaller change than it sounds — but
  it does mean a lost key or a lost Mac is a fleet-level event, which is what the
  backup key is for.

## Alternatives considered

**GitHub Actions secret.** Rejected — see above. It looks like the natural
evolution of the current workflow and quietly removes the only property worth
having.

**Enterprise Cloud.** Works, keeps keyless, costs money and requires an
enterprise-owned repo. Disproportionate for one operator, and it would still
leave the repo-takeover hole open.

**Go public.** Also works, also free, and remains the right end state — but it
forces an unrelated decision (the git history) on a schedule set by an
unconnected GitHub limitation. Worth doing on its own merits, not under duress.
The two are now independent: this ADR works in both states.

**A pure-Rust ed25519 verifier** instead of shelling out. Avoids the OpenSSH
dependency and would let faber verify inside a stripped container. Rejected for
now: it means hand-parsing SSHSIG or taking a crypto dependency, to remove a tool
that is already present everywhere faber runs — and the module already shells out
to `gh` for other reasons. Worth revisiting if a container deployment appears.

**minisign / cosign.** Cleaner formats, and neither is installed anywhere by
default, which would put "install this tool" between a host and its next security
update.
